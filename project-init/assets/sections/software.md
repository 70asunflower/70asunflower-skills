## 5. 程序项目开发流程

本项目类型含「软件」，以下流程适用。

### 5.1 顶层文档（`docs/` 下，缺一不可）

| 文档 | 回答的问题 |
|------|------------|
| `PRD.md` | 做什么、为什么做 |
| `Design.md` | 整体怎么做 |
| `TDD.md` | 技术实现（选型、架构、测试策略） |
| `开发进度.md` | 每个功能开发/测试/审核到哪一步 |

先文档后编码：开发任何功能前相应文档须已反映最新共识；需求或方案变化时先改文档再改代码。台账顶部维护「当前功能」一行，任何 agent 从这里接续，不得凭空另起炉灶。

### 5.2 串行开发，测试与审核是门禁

1. **全部登记为待办**：收到需求（哪怕一次列多个功能），先把全部功能逐条登记进台账功能表，状态一律「待办」。
2. **一次只领一个**：`待办 → 开发中 → 待测试（自测通过）→ 测试通过（验收通过）→ 已审核（人工确认）`。
3. **测试门禁**：当前功能未通过验收测试，不得开始下一个；未通过项逐条登记台账「缺陷记录」表，缺陷未全部关闭并复测通过前，不得回到「测试通过」。用户明确要求跳过时，在台账备注与当日日志记下该决定。
4. **审核门禁**：每个功能须经用户（或其指定审核人）确认后方可标记「已审核」。Agent 不得自行标记「测试通过」「已审核」。
5. **台账即事实**：状态、测试结论、审核意见、缺陷记录的任何变化实时回写；台账与实际不符视为违规。
6. **测试代码是正式代码**：放 `code/tests/`，随功能一同开发与提交，不得丢进临时区或散落根目录。

### 5.3 功能文档（一功能一文档）

每个功能一份 `docs/features/<功能名>.md`，开始开发时创建，随进展回填：

```markdown
# <功能名>

- 状态：待办  <!-- 待办 / 开发中 / 待测试 / 测试通过 / 已审核 -->
- 关联：PRD 需求第 N 项 · 代码位置 code/...

## 1. 功能说明
做什么：描述、边界、明确不做什么。

## 2. 实现思路
怎么做：方案要点、关键决策及理由、依赖。

## 3. 测试情况
| # | 测试点 | 方法 / 用例 | 结果 |
|---|--------|-------------|------|

## 4. 审核记录
| 日期 | 审核人 | 结论 | 意见 |
|------|--------|------|------|
```

工具链不兼容中文路径时，文件名可用英文 slug，文档首行标题保留中文功能名，台账「设计文档」列登记实际路径。
